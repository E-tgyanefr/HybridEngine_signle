# HybridEngine 绑定层（Binding Layer）

> 稳定 C ABI `ms_bind.h` + C# `HybridEngine.Bind`（net8.0 纯 BCL）+ Python `hybridengine`（ctypes 零第三方）。三语言走**同一 ABI、同一 API 形状**——表尾给出对称映射。

## 1. 架构（Architecture）

```
C++ 内核（App::Engine + Core + Platform + Render3D）
        ▲
        │ ms_bind.h（extern "C"，ms_ 前缀，稳定 ABI）
        │        ┌──────────────────────┐  ┌──────────────────────┐
        │        │ C#  HybridEngine.Bind  │  │ Python hybridengine    │
        │        │  P/Invoke（DllImport）│  │  ctypes（CDLL）       │
        └────────┴──────────┬───────────┴──┴───────────┬──────────┘
                            └─ 同一语义：单线程/句柄/错误码/UTF-8 ─┘
```

### 1.1 线程模型与内存所有权（Threading & Ownership）

- **单线程**：创建引擎的线程 = 主线程；跨线程调用返回 `MS_ERR_THREAD`（9）。C#/Python 的引擎、场景、组件、资产调用都应在同一线程。
- **句柄 = C++ 对象**（`ms_engine*`/`ms_scene*`/`ms_go*`/`ms_asset*`）：由 `ms_engine_destroy` 等释放；调用方**不 free**。
- **字符串 = UTF-8**：入参调用方拥有（C# `LPUTF8Str` 自动 marshal；Python `bytes`）；出参缓冲（`char* out + int cap`）调用方提供、写 NUL 结尾。
- **回调 userData**：C# = `GCHandle`（C# 拥有，`Dispose` 释放）；Python = `id(instance)`（registry 强引用保活）。
- 引擎单例计数：`ms_bind_live_engine_count()`（句柄配对断言）。

**多场景语义**（P2/SceneManager）：
- 引擎恒有 ≥1 个场景（`Scene()` 始终有效）；**所有已加载场景都参与 `Engine::Tick`**（各自 Lifecycle 全序）。
- 渲染把全部已加载场景 **合成为一趟光栅**（网格/光源/相机一起收集）——逐场景各跑一趟会各自清屏，
  只剩最后一个可见。
- `ms_scene_unload` 先走 `Scene::RemoveRoot` 拆除该场景全部对象（`OnDisable/OnDestroy` → 托管登记/
  协程/Invoke 清退）再移除槽位；**最后一个场景不可卸载**。
- **按场景入参**：`ms_scene_save/find/go_get/root_count/root_get` 一律作用于**传入的场景**
  （此前误用活动场景——单场景下不可见，多场景会读错场景）；`ms_go_add_child` /
  `ms_transform_set_parent` 作用于对象**所属场景**。
- **句柄生命周期**：`ms_scene*` 是裸指针，卸载后即悬垂；按指针成员关系判定对已释放地址本质歧义
  （地址可能被新场景复用），故**不可依赖**「对旧句柄调用会报错」。宿主卸载后应按索引重查。
- **单场景不回归**：黄金帧 `4634E387E024BE90` 逐位不变（bind 用例专门断言）。

| 函数 | 说明 |
|---|---|
| `ms_go_instance_id` | 对象 InstanceId（ms_id） |
| `ms_go_set_active` | 激活（联动组件 OnEnable/OnDisable） |
| `ms_go_destroy` | 延迟销毁（帧尾队列） |
| `ms_go_add_child` | 子对象（outGo） |
| `ms_component_register` | **注册组件回调表**`ms_component_spec*`（见 2.4） |
| `ms_go_add_component` | 按 scriptType 挂到对象（须先 register） |
| `ms_go_get_component` | 取脚本组件（outReflected——脚本桥） |
| `ms_component_set_enabled` | **P1-a：组件级开关**（`Component::SetEnabled` → `LifecycleDriver::SetActive`） |
| `ms_component_get_enabled` | P1-a：读组件开关（未找到=NOT_FOUND，出参置 0） |
| `ms_go_has_component` | **P1-b：组件存在性查询**（原生+脚本统一口径；缺失不算错误=OK+0） |
| `ms_engine_set_frame_hook` | **P1-a：引擎帧钩子**（托管每帧服务——phase 0 帧首/1 帧尾，每帧 Tick 各一次） |

**P1-a 组件级 enabled 语义**：置 `0` 后 `LifecycleDriver::Tick` 跳过该组件（`Start/FixedUpdate/Update/LateUpdate` 均不分派），
并触发一次 `OnDisable`；置回 `1` 触发一次 `OnEnable`；**同值赋值=空操作**（不重复回调）。
处于禁用态且**尚未 Start** 的组件，其首次 `Start` 被抑制，恢复启用后的首个 Tick 才补触发（每个组件仍只 Start 一次）。
`scriptType` 查找口径与 `ms_go_remove_component` 一致：脚本组件 = per-instance 注册键（`FullName#N`），C++ 组件 = RTTI 类型名。

**P1-a 帧钩子**：每帧 `Engine::Tick` 内按相位调用两次——`phase=0`（帧首，Time 已推进、组件回调之前）供托管侧
同步 `Time.deltaTime/time/frameCount`；`phase=1`（帧尾，Lifecycle 全序之后、Events Flush 之前）供托管侧推进
`Invoke`/协程。存在的理由：托管每帧服务若只挂在 `GameEngine.RunFrame` 上，**编辑器 Play 直驱 `Engine::Tick`
的路径永远不会执行它**（Invoke/协程会静默不跑）。`cb=null` 解绑；重复注册=替换。

**P1-b 组件存在性查询**：`ms_go_has_component` 用与 `ms_go_remove_component` 相同的查找口径，同时覆盖
原生组件（RTTI 注册名，如 `MeshVisual`）与脚本组件（per-instance 注册键 `FullName#N`）。
**查询语义**：缺失不算错误——对象句柄有效 → `MS_BIND_OK` 且 `outPresent=0/1`。

**P1-b 一并修正：`ms_go_destroy` 此前不真正移除对象。** 帧尾销毁队列原先只对组件跑
`OnDisable`/`OnDestroy`，**从不把对象从 `Scene::roots_` 摘除**——调用方以为对象已销毁，实际它仍留在场景里
（仍参与渲染与枚举）。现改为经 `Scene::RemoveRoot` 收口：含子树移除、与父级摘净（避免父级 `children_`
留悬垂指针）、`LifecycleDriver::SequenceLog` 轨迹与编辑态直删路径一致，并**幂等**（重复销毁 / 父子同入队列
时，后一次指向已释放内存的调用被安全跳过而不是 use-after-free）。

### 2.4 组件回调表（`ms_component_spec`）

```c
typedef struct ms_component_spec {
    const char* scriptType;    // 注册键（C#：FullName#n——多实例安全；Python：QualName#n）
    ms_cb_void  onAwake;       // void (*)(void* ctx)
    ms_cb_void  onEnable;  ms_cb_void  onStart;
    ms_cb_void  onDisable; ms_cb_void  onDestroy;
    ms_cb_dt    onUpdate;  ms_cb_dt    onFixedUpdate;  ms_cb_dt    onLateUpdate;
    void*       userData;      // C# GCHandle / Python id(instance)
} ms_component_spec;
```

流程（标准两步，与 C++ `AddComponent<T>` 等价）：`ms_component_register(spec)` → `ms_go_add_component(e, go, scriptType)`。回调同步于主线程（引擎 Tick 内）。

### 2.7 脚本桥（C# Script Bridge，5）—— M3.4 / P1-a

| 函数 | 说明 |
|---|---|
| `ms_script_bridge_register` | 注册三回调（fields/set/types — `ms_cb_script_*`） |
| `ms_script_fields` | 按 instanceKey 取字段 JSON（编辑器 Inspector 用） |
| `ms_script_field_set` | 按 instanceKey 写字段（JSON 值） |
| `ms_script_types` | 已注册脚本类型名 JSON 数组 |
| `ms_script_replay_register` | **P1-a：脚本组件重放回调**（场景加载——`scriptFields` → 托管实例重建） |

**P1-a 场景加载脚本组件重放**：脚本组件的字段活在托管实例上（C++ 侧无副本），场景里只存
「保存时的 per-instance 注册键 + `scriptFields`」。`ms_scene_load` 在桥 + 重放回调都就绪时：

1. 反序列化按**注册键形状**（`*#数字`）认领脚本条目，建**静默占位**组件
   （占位不接任何回调——否则反序列化触发的 Awake/OnEnable 会拿旧场景遗留的 GCHandle
   去回调正在被拆除的旧实例）；
2. 旧场景经 `Scene::RemoveRoot` 拆除（触发 OnDisable/OnDestroy → 托管登记/协程/Invoke 清退）；
3. 装载新场景后逐条调用重放回调：托管侧按注册键解析类型、重建实例、**按原注册键**重新
   `ms_component_register`（`BindComponent` 持 spec 指针 → 就地生效）、补挂 Owner 视图、回填 `scriptFields`。

注册键**沿用保存值**（不重新分配）→ 再次保存时 `type` 不漂移，round-trip 幂等。
未注册重放回调时脚本条目**不被认领**——`ms_scene_load` 仍返回 `MS_ERR_NOT_FOUND`（不静默降级）。

### 2.8b .NET 脚本承载（Project Scripts，5）—— P2

| 函数 | 说明 |
|---|---|
| `ms_dotnet_status` | 探测承载环境（hostfxr + dotnet CLI）→ 1=可用 0=不可用（文案写入 outInfo） |
| `ms_scripts_build` | 生成 `<root>/Library/ScriptAssemblies/*.csproj` + 外部 `dotnet build` |
| `ms_scripts_load` | hostfxr 载入 ScriptLoader → 注册脚本桥 → 返回可挂类型全名 JSON 数组 |
| `ms_scripts_add_component` | 按托管类型名给对象挂项目脚本组件 |
| `ms_scripts_unload` | 卸载（可收集 ALC——支持「改脚本→重编译→重载」） |

**零第三方**：`hostfxr`/`coreclr` 是 .NET 运行时自带组件（系统库性质，同 D3D11/XInput），
编译走外部 `dotnet build` 子进程——**不内嵌 Roslyn**。无 dotnet 的机器上 `ms_dotnet_status` 返回 0，
编译/加载返回负值，编辑器据此降级（脚本目录不可用），不影响既有功能。

**单引擎同一性（关键约束，实测踩坑）**：编辑器静态链接 `hybridengine_bind`（引擎在 exe 内）。
托管侧若按常规 `[DllImport("hybridengine")]` 解析，会再加载一份 `hybridengine.dll`
→ 出现**第二套** `Bridge()/SpecTable()/引擎注册表`，脚本操作不到编辑器那棵场景树。
故 `ms_scripts_load` 传入「宿主模块路径」（缺省=本代码所在模块，经 `GetModuleHandleEx(FROM_ADDRESS)` 取得），
由 `HybridEngine.ScriptLoader` 装 `DllImportResolver` 把 `hybridengine` 指回**同一模块**。
宿主 exe 因此必须导出 `ms_*` 符号——**MinGW 下由 `hybridengine_bind` 静态库内 `MS_API(dllexport)` 精确导出**；
不再用 `-Wl,--export-all-symbols`（LTO 会把编译器生成的模板弱符号导出到错误地址，托管 P/Invoke 会崩）。

**其它实测要点**：
- Windows 上 hostfxr 的 `char_t` 是 **`wchar_t`**：`hostfxr_initialize_for_runtime_config` /
  `load_assembly_and_get_function_pointer` 必须传宽串，传窄串会得到乱码路径错误。
- 入口用**公有委托类型名**（`LoadFn`/`AddComponentFn`/`UnloadFn`）而非 `UNMANAGEDCALLERSONLY_METHOD`：
  后者签名不匹配时只回报语焉不详的 HRESULT。
- 项目脚本装进**可收集 ALC**，但 `HybridEngine.Bind` 必须返回宿主已加载的**同一实例**，
  否则 `is ComponentBase` 会因两份 Bind 永远为 false。
- csproj 的 `<Compile Include>` 必须写**绝对路径**（msbuild 相对 csproj 目录解析）。
- 项目脚本编译输出目录 = `Library/ScriptAssemblies`（`OutputPath=$(MSBuildThisFileDirectory)`），
  与 csproj 同目录，产物即 `HybridEngine.ProjectScripts.dll`。
- **宿主在进程内直接构造引擎时必须先调 `ms_bind_attach_host()`**（见 §2.1）：
  编辑器这类宿主不走 `ms_engine_create`，不登记则所有 `MS_ABI_GUARD` 保护的调用都返回 `MS_ERR_THREAD`
  （实测症状：`ms_scripts_build` 立即失败且日志缓冲为空——很难定位）。
- `ms_scripts_load` 同时负责把**托管每帧服务**（Time 同步 / Invoke / 协程）挂到宿主引擎帧上
  （`ManagedFrame.Register`）。漏掉则脚本「跑了但 `Time.deltaTime` 恒 0、Invoke/协程永不推进」，
  且因为不报错而极难发现——`ManagedFrame.Register` 现已对失败路径给出显式告警。

### 2.8c 脚本重放 / 快照收口（`src/bind/script_host.hpp`）—— P2

编辑器 Play/Stop 的快照往返走**自己的** C++ 反序列化，不是 `ms_scene_load`。为免两套实现漂移，
脚本相关流程收在 `HybridEngine::Bind::Script`：

| 函数 | 说明 |
|---|---|
| `HostingActive()` | 桥已注册 **且** 重放回调已装 → 可认领并重放脚本组件 |
| `LooksLikeScriptKey()` | 注册键形状 `FullName#N` 判定（区分脚本组件与真正的未知类型） |
| `LoadInto(Scene&, text)` | **容器文本 → 就地装入场景（含脚本重放）——唯一推荐入口** |
| `SerializeForSnapshot(scene, out)` | 场景 → 容器文本（桥激活时并入 `scriptFields`，与 `ms_scene_save` 同口径） |

**`LoadInto` 内部顺序不可调换**：① 反序列化（脚本条目=静默占位）→ ② 拆除 target 现有内容
（旧实例在此收到 `OnDestroy`，用的仍是**旧**回调）→ ③ 装入新场景 → ④ 逐条托管重放（同键覆盖回调表 +
回填 `scriptFields`）+ 占位补挂。若把 ④ 提前到 ② 之前，重放覆盖后的回调表会让旧实例的
`OnDisable/OnDestroy` 打到刚重建的新实例上——旧实例的销毁通知静默丢失（bind 用例专门守这条）。

### 2.11 GUI 平面（Draw Plane，24）—— t1

**帧序（录播式·定稿）**：`ms_rnd_*` 与 `ms_text_*` 统一为**命令录制**（录制时数据立即归 Op——`ms_text_draw` 录制时 GDI 光栅化一次（t10：掩码=共享缓存引用+引用计数 pinned——Op 零拷贝共享；cache 淘汰后回放仍安全）、`ms_rnd_blit_rect`/`ms_rnd_blit_alpha` 拷像素；回放零系统调用=严格确定性）；`ms_engine_render` 先黑底 Clear→按序回放（parity 面 + 窗口面同命令，Participates in 哈希）。**命令不跨帧残留**——host（C#/Python `GameEngine`）每帧帧首调 `ms_rnd_clear_list`，帧序 = 清列表 → 回调录制本帧命令 → `ms_engine_render`（回放+哈希，本帧命令同帧可见）；空命令 = 黄金路径逐位不变，零回归。

### 2.12 音频（Audio，8）—— t3

**语义**：WinMM（mci）桥接——句柄=引擎拥有（`ms_engine_destroy` 释放全部，不必显式 close；单线程——跨线程=MS_ERR_THREAD）；时基=毫秒；状态机=closed→open→playing→paused（`is_open` 沿用后端语义）。`ms_audio_open` 返回：**≥10 = 句柄 id**（槽位句柄——与 `MS_ERR_*` 正值 1..9 错开防歧义；0=不合法）；失败=错误码（文件不存在=MS_ERR_NOT_FOUND；后端打开失败=MS_ERR_IO）。句柄 close 后全部调用=MS_ERR_NOT_FOUND。错误码复用既有（未新增）。

## 5. 三语言 Parity

渲染核同路径同参数 → 三语言哈希一致（回归锚点 `4634E387E024BE90`，1280×800——空命令黄金帧；GUI 平面绘制锚点 `855D0AC4CBCD78C2`——t-text-native 后实测；C#/Python 同命令同值——minimal_gui_cs/minimal_gui_py 验证同值 `855D0AC4CBCD78C2`）：
> ⚠ **锚点与"窗口/游戏默认分辨率"无关**（2026-09-18 实测澄清，此前这里写"默认 1280×720 窗→视图 scale=0.9"是**误导**）：
> 示例是 **headless**（`windowed=false`）⇒ 只存在 parity 面，`WindowViewport()` 命中"无窗口渲染器 → 返回恒等 {1,0,0}"这条分支
> （见 `engine.cpp`），命令按 **scale=1** 回放到固定的 **1280×800 parity 面**。
> 故把游戏默认分辨率从 1280×720 改成 **1080P（1920×1080）**后，本锚点**仍逐位不变**（实测 5/5 示例全过）。

### 6.1 同键双实例的派发串线（H2）—— ✅ 已修复（2026-09-21）

**症状**：对象 A 挂着脚本组件（注册键 `Foo#1`）仍存活时，**附加加载**一份同样含
`Foo#1` 的场景 → 重放实例与 A **共用**同一个注册键，于是：

- `SpecTable["Foo#1"]` 被重放就地覆盖 → A 的 `BindComponent` 改调重放实例的回调（A 的 `Update` 丢失）
- `ScriptRegistry` 同名覆盖 → `Find("Foo#1")`、字段读写、`script.call` 也全部落到重放实例
- 结果：重放实例拿到两次派发（自己的 + A 的）

**为什么不能"改成唯一键"**：注册键是**写进场景文件**的 `type` 字段，
重放**必须沿用它**，否则再次保存时 `type` 会漂移、破坏场景 round-trip
（`CsTestRunner` 明确断言"重放：注册键沿用（再次保存无漂移）"）。
所以"同键"是契约层面的必然，不能靠改键回避。

**修法**（不动注册键语义、不动序列化格式）：把原生 spec 表由「按类型键」改为
「按 **(类型键, 宿主对象)** 键控」，每个实例有自己的一份回调表：

- 表键：`std::map<std::pair<std::string, void*>, SpecEntry>`；`owner=nullptr` 即旧的
  "按类型共享"语义（向后兼容，旧入口 `ms_component_register` 行为不变）。
- 新导出 `ms_component_register_for(e, owner, spec)`：为指定对象注册专属 spec。
- `ms_go_add_component` 优先取该对象的专属条目，取不到再退回共享条目。
- 重放补挂由"按类型键查"改为 `BindComponent::RebindToOwnEntry()`：
  按 (类型键, 本组件 `Owner()`) 取**自己的**条目。
- C# `ComponentBridge` 与 Python `_EngineRegistry` 的"新建/重放"两条路径都走新入口
  （Python 用符号探测，旧 DLL 时自动退回）。

⚠ **两个容易踩回去的点**（都实际踩过）：
1. `Rebind` 若退回"按类型键查"，本修复立即失效——必须走 `RebindToOwnEntry()`。
2. `InjectScriptFields`（决定 `scriptFields` 是否写入场景）判定"该键是否已注册"时，
   **不能只查共享条目**：专属键控后共享条目通常不存在 → `scriptFields` 从不写入场景
   → 症状是"重新加载字段全丢，而注册键沿用却正常"。故用 `IsScriptKeyRegistered()`
   （共享或任意专属条目都算命中）。

**回归用例**：`CsTestRunner` ⑫b —— A 挂脚本（Hits=11）→ 保存 → 附加加载同键场景
（A 仍存活）→ 跑 3 帧后断言两实例**各自** +3 次 Update、且按 A 的键读到的是 A 的字段。

### 6.2 Python 参与场景重放（H4）—— ✅ 已修复（2026-09-21）

**症状（修复前）**：用 Python 存一个含 Python 组件的场景，再 `load_scene` → 报
`MS_ERR_NOT_SUPPORTED`（此前还是误报 `MS_ERR_NOT_FOUND`，错误码已先修正）。

**原因（链条）**：`Script::HostingActive()` 要求**桥 + 重放回调都就绪**；
Python 此前只包装了组件生命周期（`PyComponentBase` 八回调），**没有**注册
`ms_script_bridge_register`（fields/set/types 三回调）。故承载判定为未就绪 →
`ms_scene_load` 走普通路径 → 脚本键无人认领 → 不静默降级，直接报错。

**修法**：新增 `python/hybridengine/script_bridge.py`（与 C# `CsScriptBridge` +
`SceneReplay` 对称），实现四个回调并在 `GameEngine.__init__` 里注册：

| 回调 | 作用 | 实现要点 |
|---|---|---|
| `fields` | 组件 → 字段 JSON | 只收 public 且非可调用的属性，类型限 `{bool,int,float,str,三元数值序列}`；用 `json.dumps` 做转义（C# 那边手写引号**不转义引号字符**，Python 侧走标准转义更稳） |
| `set` | 字段 JSON → 组件 | 按**现有字段类型**定型；拒绝下划线开头/可调用名（不让脚本桥写成任意属性） |
| `types` | 类型清单（节点图调色板） | 取本引擎注册表里的实例类型名，**排序**输出保证跨进程稳定 |
| `replay` | 场景加载重建实例 | 解析类型 → 实例化 → 建 Owner 视图 → `bind_existing`（按 (键, 对象) 补挂）→ 回填字段 → `awake`/`on_enable` |

⚠ **三个必须记住的点**（实现时逐个踩到并修掉）：

1. **回调对象必须强引用保活**：`CFUNCTYPE` 一旦被 GC 回收，C++ 侧存的就是已释放的
   libffi 闭包 → 崩溃。故桥对象挂在 `GameEngine` 实例上（`engine._script_bridge`）。
2. **旧实例必须注销**：场景重载 = 先拆旧场景（旧实例收 `on_destroy`）再重放；
   若不移除，注册表里会**同时留着旧实例与重放实例**（同键两条），
   `find_by_key` 可能命中已死的那个 → 脚本桥字段读写读错对象。
   实现为 `PyComponentBase.__init_subclass__` 自动给子类 `on_destroy` 包一层注销
   （C++ 侧只调 `on_destroy` 这一个回调，没有别的可靠钩子）。
3. **`hostingActive` 是两条路径的开关**：注册桥之后 `ms_scene_load` 才会走"脚本重放"路径；
   反过来，注册了桥之后**含脚本键的场景不再走"普通加载"**——这是预期行为（不静默丢脚本）。

**回归用例**：`python/tests/test_py_bind.py::test_scene_roundtrip_with_python_component`
—— 存含 Python 组件的场景 → 加载回来，断言：旧实例收到 `on_destroy`、
注册表只剩重放实例（长度 1）、字段全部还原、重放实例参与 Update 分派。

**至此 §6 无「有意保留的限制」**；§6.1/§6.2 保留为已修复项的成因记录，
防止后人把关键实现"简化"回去。
